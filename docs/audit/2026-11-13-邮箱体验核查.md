### 3.3 `mail_list` 缓存优先的并发安全（通过，无死锁）

这是本核查重点看的地方，结论是**没有死锁风险**，理由如下：

1. `mail_list` 在缓存命中分支里**先 `drop(session)` 再调 `start_mail_refresh`**（`src-tauri/src/commands.rs:2436-2448`）。`start_mail_refresh` 内部才 `session.lock()`（`:2533`），锁序是「释放后重新获取」，不是「持锁再获取自己」。
2. `lock_session` 用的是 std 的可重入**非**语义互斥量（`src-tauri/src/lock.rs:75-84`），同一个线程二次 `lock` 会自死锁 —— 所以上面那个 `drop` 是必需的，实现做对了。
3. 后台线程只在读候选 UID、读 DEK/vault 句柄、写每条正文时短暂持锁（`:2533-2553`、`:2676-2703`），**不跨网络往返持锁**：`io.transact` 在锁作用域之外。这一点与 `mail_body` 的既有写法一致。
4. `mail_prefetch` 与 `mail_list` 的台后台刷新**共用同一个 `mail_refresh_lock()`**（`:2525` 用 key `list:{entry}:{folder}`，`:2670` 用 key `prefetch:{entry}:{folder}`）。key 前缀不同，所以不会互相吞掉，也不会互相阻塞。
5. `MailRefreshLock::acquire` 用 `HashSet::insert` 的返回值判断归属（`:2581-2586`），语义正确；`release` 在 `thread::spawn` 的尾部无条件执行（`:2562`、`:2719`），即使 `fold()` / `run()` 返回 `Err` 也会走到，不会泄漏 key。

一处**轻微**问题（不单独列为缺陷）：`acquire` 成功但 `thread::spawn` 本身 panic（极罕见）时 key 会永久残留，该账号+文件夹的后台刷新从此静默失效。风险低，但把 `spawn` 放进 `catch_unwind` 或在 `spawn` 前不做 `acquire` 会更干净。

## 4. 缺陷清单

### D-1（已撤销）：`beforeUid` + 缓存优先不漏页

**初判**：怀疑 `mail_list` 缓存命中时把 `request.before_uid` 原样透传给 `mail_list_local`（`src-tauri/src/commands.rs:2427`、`src-tauri-mobile/src/commands.rs:1351`），会导致「加载更早」从列表中间开始、漏掉一整页。

**逐路径推演后撤销**。关键是本地分页与服务器分页用的是同一个不变量：

- `list_local` 的 `WHERE ... AND uid < ?3 ORDER BY uid DESC LIMIT ?6`（`mail_store.rs:498-524`）；
- 服务器的 `recent_uids(..., before, limit)` 同语义（`mail.rs:766-780`）。

即「`before` 是排他上界」。因此无论这次分页来自缓存还是服务器，返回的都是「比 `before` 更早的最新 50 条」，两者可互换，不存在从中间开始的可能。

**推演中最接近出问题、实际不成立的路径**：缓存里已有 301…102（200 行），列表显示第 1 页 301…252，用户点「加载更早」（`oldest=252`）→ 缓存命中 → 返回 251…202（正确）→ 再点 → `oldest=202` → 返回 201…102（正确）。缓存命中反而省了一次网络。

**附带发现的可读性隐患**（不构成缺陷，归入 §6「建议顺手改」）：

```js
// src/App.vue:2222 / apps/mobile/src/App.vue:492
mailCacheCached.value = result.cached && !older.length;
```

逻辑是对的（`result.cached && older.length === 0` 表示「服务器说没有更早的了，列表仍是缓存页」），但 `!older.length` 的意图和变量名对不上，容易被后来者误改。

### D-2（必须修）后台刷新只写最新 50 条，会在缓存里留下正文空洞

**证据**

- `src-tauri/src/commands.rs:2525-2562` `start_mail_refresh`：拉 `limit=50`、`before_uid=None` 的一页，然后 `mail_upsert_messages(...)`（`:2553`）。
- `src-tauri/src/commands.rs:2885` `sync_account` 同样只拉 50 条（`:2872-2882`）再 `mail_sweep_folder(keep=300)`（`:2885`）。
- `upsert_messages` 的 `ON CONFLICT` 分支**覆盖** `subject/from_addr/date/seen/flagged/has_attachment`，`preview` 用 `CASE WHEN excluded.preview='' THEN mail_messages.preview ELSE excluded.preview END` 保留旧值（`mail_store.rs:322-357`）。`body_text`/`body_html`/`body_fetched_at` 不在 `SET` 里，所以正文**不会**被覆盖成 NULL。
- `sweep` 用 `uid NOT IN (最新 keep 个)` 删除，**只按 UID 排序，不看 `body_fetched_at`**（`mail_store.rs:610-633`）。

**缺陷本体**：`sweep(300)` 与「后台刷新只写最新 50 条」叠加后，被淘汰的 250 条里有用户**已经读过、正文已缓存**的行。下一次 `mail_sync` 会删掉它们连同正文。用户重新点「加载更早」并点开同一封信时，`mail_body` 缓存未命中 → 重新走 IMAP。

这与规格 §3.2「`sweep`：`pins`（星标、**最近打开过的**）额外保留」不符 —— **实现里 `pins` 从来没被用上**：`src-tauri/src/commands.rs:2885` 和 `src-tauri-mobile/src/commands.rs:1667` 两处调用都传 `&[]`，全仓没有任何地方用「最近打开过」构造 `pindowns`。`set_pinned` 也没有调用者（`grep -rn "mail_set_pinned\|set_pinned" src-tauri src-tauri-mobile` 只命中定义）。

**后果排序**

1. 星标邮件和刚读过的邮件，正文缓存会被 `sweep` 无差别删掉，用户下次打开重新拉。功能没坏，但「点开即显」的体验承诺（规格 §1 第 1 条）在最常见的「日常收信 → 一个月后回看」路径上失效。
2. 更糟的是 `mail_sync` 只缓存最新 50 条的元数据，但 `sweep(300)` 保留 300 行 —— 剩下的 250 行是历史残留。它们会一直占着位置直到被刷新的 50 条挤出去，形成「缓存里 90% 是永远不会被刷新、正文也早被删掉」的死行。

**根因**：`sweep` 的取舍维度（纯 UID）和业务意图（保留「最近打开过」的）不一致；`pins` 参数设计出来了，调用点没接。

**最小修复**（二选一，都不改只读承诺）

方案 A（推荐，改动最小）：在 `sync_account` / 移动端 `mail_sync` 调用 `sweep` 时传入真实 `pindowns`：

```rust
// src-tauri/src/commands.rs:2885 附近
let pindowns: Vec<u32> = vault
    .mail_recent_body_uids(entry_id, &folder.name, 50)   // 新增：body_fetched_at IS NOT NULL ORDER BY body_fetched_at DESC LIMIT 50
    .map_err(map_err)?;
let _ = vault.mail_sweep_folder(entry_id, &folder.name, MAIL_SYNC_KEEP, &pindowns);
```

移动端 `src-tauri-mobile/src/commands.rs:1667` 同样处理。

方案 B（把口径写进 SQL）：让 `sweep` 自己按「最新 `keep` 个 OR `body_fetched_at IS NOT NULL` OR `flagged<>0`」判断，`pindowns` 参数删掉。这需要改 `mail_store.rs:620-631` 的 `DELETE ... WHERE` 子句：

```sql
DELETE FROM mail_messages
 WHERE account_id=?1 AND folder=?2
   AND uid NOT IN (SELECT uid FROM mail_messages
                   WHERE account_id=?1 AND folder=?2 ORDER BY uid DESC LIMIT ?3)
   AND pinned_at IS NULL
   AND body_fetched_at IS NULL   -- 新增：正文已缓存的保留
   AND flagged = 0               -- 新增：星标保留
```

方案 B 更彻底，但会让 `sweep` 的删除量依赖用户行为，缓存上限不再是硬上限。**建议方案 A**，它同时兑现规格 §3.2 对 `pins` 的承诺。

### D-3（必须修）`sync_account` 抛错时 `mail_sync` 整轮中止，已写入的更新不回滚也不上报

**证据**

- `src-tauri/src/commands.rs:2838-2889` `sync_account` 用 `?` 一路短路，任何一封文件夹出错（`list_folders` 失败、`list_folder` 失败、`unread_count` 失败、`vault` 写失败）都会让整个函数返回 `Err`。
- `src-tauri/src/commands.rs:2806-2830` `mail_sync_blocking` 里 `match sync_account(...) { Err(_) => entry.failed = true }`（`:2817-2820`）只把该账号标记为失败，**但此时前面几个文件夹的 `mail_upsert_messages` / `mail_save_folders_unread` / `mail_sweep_folder` 已经写进库了**。
- 更关键的是 `:2823-2828`：所有账号跑完后，`mail_badge_unread()` 若失败，整个 `mail_sync_blocking` 返回 `Err`，前端 `refreshMailNow` 的 `catch` 把 `mailError` 显示出来，用户看到「收取失败」，但**实际上已经收了一部分**。

移动端 `src-tauri-mobile/src/commands.rs:1649-1675` `mail_sync` 用的是 `let _ = ...` 逐个忽略错误，行为**相反**：单点失败静默跳过、整体返回 `Ok`。两端对「部分失败」的语义不一致。

**根因**：桌面端把「取文件夹列表」和「逐个文件夹同步」放在同一个 `Result` 链里，粒度太粗；移动端粒度太细（连 `insert` 失败都吞掉）。

**最小修复**

1. `sync_account` 改成逐文件夹 `match`，单个文件夹失败只记进 `report`，不短路：

```rust
for folder in folders.iter().filter(|f| matches!(f.role, "inbox" | "archive")) {
    if let Err(e) = sync_one_folder(state, entry_id, &mut io, &mail, folder) {
        // 记入 entry.failed / entry.error，继续下一个文件夹
    }
}
```

2. `mail_sync_blocking` 把 `mail_badge_unread()` 失败降级为 `Ok(0)` 或保留上次的 `report.unread`，不要因此让整个命令失败。
3. 两端统一成同一份语义，并写进 `Docs`：**多个文件夹 → 部分成功是正常态，`failed` 只标到具体账号**。

### D-4（应当修）`mail_prefetch` 返回值语义变了，两个前端都在误报

**证据**

- 后端注释（`src-tauri/src/commands.rs:2636-2641`）明确写了：「返回值是**接受的 pass 数**：排队成功返回 1，已有同账号+文件夹在飞返回 0」，正文实际写入数通过 `mail-page-refreshed` 的 `bodies` 字段发出（`:2714-2721`）。
- 移动端 `src-tauri-mobile/src/commands.rs:1519-1528` 直接 `Ok(1)` / `Ok(0)`，但那段代码**不发任何事件**。
- 前端仍然把返回值当封数用：
  - `src/App.vue:2154-2157`：`if (seq === mailPrefetchSeq || count <= 0) return; ... mailSyncNote = \`已缓存 ${count} 封正文\``
  - `apps/mobile/src/App.vue:359-362`：同样的写法。
- 两个前端**都没有** `listen("mail-page-refreshed")`（`grep -rn mail-page-refreshed src/ apps/` 无命中）。

**后果**：每次进入邮箱预热成功，界面固定显示「**已缓存 1 封正文**」，无论实际写了 0 封还是 5 封。移动端因为不发事件，连「真实写入数」都拿不到 —— 永远只有 1。

**根因**：后端从同步改异步时把返回值含义换了，前端契约没同步更新；规格 §4.2/§7 也没定义这个返回值。

**最小修复**（三选一）

- 方案 A（改动最小，推荐）：前端不再显示这个数字。`warmMailBodies` 的 `.then` 只用来判断「是否已有一轮在跑」，删掉 `mailSyncNote = \`已缓存 ${count} 封正body\`` 这句提示。预取本来就是静默加速，不提示才符合规格 §4.2「预取失败一律静默」，成功也不必打扰。
- 方案 B：前端加 `listen("mail-page-refreshed")`，用 `event.payload.bodies` 显示真实数字；移动端后端补上 `app.emit`（需要给移动端 `mail_prefetch` 加 `AppHandle` 参数，签名会变，要同步两端契约文档）。
- 方案 C：把 `mail_prefetch` 退回同步实现，返回真实写入数。这会重新引入「持锁跨网络」的等待，**不建议**。

### D-5（应当修）规格与实现的返回值口径不一致

`docs/superpowers/specs/2026-11-13-mail-ux-parity-design.md:70` 写「新命令 `mail_prefetch(entryId, folder, limit?)`：……并发取 `BODY.PEEK[TEXT]`，写进缓存」，§7 表格写「`mail_prefetch` 有 / 有」，没有定义返回值；但实现（`commands.rs:2636-2641`）已经把返回值定成 `0|1`。

同时规格 §4.2 说预取用 `BODY.PEEK[TEXT]`，实现用的是 `fetch_body_in`（`mail.rs:1435`，`BODY.PEEK[]` 整封）。整封取比 `[TEXT]` 略重，但能一次性拿到 HTML + 纯文本 + 结构，比 `[TEXT]` 更贴合「点开即显」。**这是实现优于规格，但规格没同步。**

**建议**：合并前把规格 §4.2/§7 改成实现的实际行为（`BODY.PEEK[]`、返回 `0|1`、真实封数走 `mail-page-refreshed`），避免下一个实现者按过时规格改回去。
