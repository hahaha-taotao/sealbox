## 目标
新增一个受控的 `github_create_release` MCP 工具，让 Sealbox 能通过已保存的 GitHub Token 创建 GitHub Release（同时由 GitHub API 按 `tag_name` 创建 Tag），并把后续值得补齐的 GitHub 接口按风险和优先级整理进项目文档。

## 实现方案

### 1. 增加独立的 GitHub API 写入开关
修改 `src-tauri/src/github_mcp.rs`、`src-tauri/src/commands.rs`、`src/lib/tauri.ts` 和 MCP 设置页 `src/App.vue`：

- 将 `GithubMcpPolicy` 扩展为 `enabled` + `api_write_enabled`。
- 旧策略 JSON 缺少新字段时默认 `false`，保持向后兼容且默认不开写权限。
- 现有本地 Git 工具继续由 `enabled` 控制，避免改变已有 `stage/commit/push/pull/clone` 行为。
- `github_create_release` 只有在 `enabled && api_write_enabled` 时可见、可调用。
- MCP 设置页增加单独的“允许 GitHub API 写入（创建 Release）”开关和明确的高风险说明；关闭时工具不出现在 `tools/list`。

### 2. 注册 `github_create_release` 工具
在 `src-tauri/src/github_mcp.rs`：

- 新增写工具定义 helper，明确标记 `readOnly: false`、`risk: "high"`，不要复用当前固定为只读低风险的 `tool()`。
- 使用闭合 JSON Schema（`additionalProperties: false`），参数限定为：
  - `credential_id`、`owner`、`repo`、`tag_name` 必填；
  - `target_commitish` 可选，限制为合法分支名或 SHA 形式的短字符串；
  - `name`、`body` 可选且有长度上限；
  - `draft`、`prerelease`、`generate_release_notes` 可选，业务层显式检查布尔类型；默认 `draft=true`、其余为 `false`。
- 不接受任意 URL、HTTP method、headers 或 raw body。
- 发布为非草稿时仍属于高风险调用，但必须由调用方显式传 `draft:false`；默认创建草稿，避免模型无意公开发布。

### 3. 增加受控 POST 请求路径
在 `github_mcp.rs`：

- 保留现有 GET helper 不变，新增仅供固定 GitHub Release endpoint 使用的 POST JSON helper；不泛化为任意 HTTP 工具。
- 固定目标为 `https://api.github.com:443/repos/{owner}/{repo}/releases`，继续使用 `PublicResolver`、公网地址校验、无重定向、连接/请求超时、响应大小上限、GitHub API 版本头和 Token 脱敏。
- 请求体只由已验证参数构造，设置 `Content-Type: application/json`。
- 正确处理成功状态 `201`，并让 `GithubCallResult.status` 记录真实 HTTP 状态，审计不再固定为 `200`。
- 新增受限 Release DTO，只返回 `id`、`tag_name`、`name`、`draft`、`prerelease`、`html_url`、`target_commitish`、`published_at` 等非敏感字段，不透传完整原始响应。
- Release 的 tag/仓库信息进入现有审计上下文；body、Token 和完整响应不写入审计。

### 4. 加强参数验证和策略测试
在 `github_mcp.rs` 及相关测试中：

- 补齐通用布尔类型校验，避免 `draft/prerelease/generate_release_notes` 传入字符串或数字时漏过 schema。
- 增加 tag、target、name/body 长度、非法字符、空 Token 的纯函数测试。
- 更新“全部 API 工具都是只读”的旧测试，改为分别断言只读工具和高风险写工具契约。
- 测试策略关闭、写入开关关闭、金库锁定、错误凭据时均拒绝 Release 工具。
- 测试助手的安全过滤仍排除 `readOnly:false/risk:high` 的 Release 工具。
- 测试工具 schema 闭合、工具目录数量和审计状态码处理。

### 5. 更新文档并梳理后续接口
新增一份 GitHub MCP 路线文档（放在 `docs/superpowers/specs/`），并同步更新 README 的 MCP 部分：

- 记录 `github_create_release` 的参数、默认草稿行为、双开关和安全边界。
- 按优先级整理后续接口：
  - P0 只读：PR 详情/files/commits/reviews/checks、Release 列表/详情/assets、Tags、commit compare、Actions runs/jobs；
  - P1 普通写入：创建 Draft PR、Issue/评论；
  - 高风险：发布 Release、上传/删除 Release assets、workflow dispatch/rerun/cancel、Tag/分支/Contents 写入、合并 PR。
- 明确暂不提供任意 HTTP、GitHub Contents 写文件、Secrets/Webhooks 和自动合并；这些需要独立权限、逐次确认和更完整的 HTTP mock 测试。
- 修正 README 中助手实际可见工具数量和高风险工具不会进入助手的说明。

### 6. 验证
实现完成后运行：

- `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`（记录仓库既有格式差异，不为本功能重排无关文件）；
- `cargo test --manifest-path src-tauri/Cargo.toml`；
- `npm run build`；
- `node --test extension/fill-logic.test.js`；
- `git diff --check` 与工具定义/策略测试。

不创建 Release、不推送、不提交，除非后续用户明确要求；本次只实现工具和文档。
