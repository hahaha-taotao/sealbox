按 Tauri 官方签名 updater 路线实现，目标是：应用内检查更新 → 下载进度 → 签名校验 → 启动安装 → 重启应用；不再把安装包交给系统浏览器，也不让前端直接下载/执行任意 `.exe`。

## 1. 接入 Tauri updater 与重启插件

- 在 `package.json` 增加 `@tauri-apps/plugin-updater` 和 `@tauri-apps/plugin-process`，版本与当前 Tauri 2 对齐；更新 `package-lock.json`。
- 在 `src-tauri/Cargo.toml` 增加 `tauri-plugin-updater` 与 `tauri-plugin-process`。
- 在 `src-tauri/src/lib.rs` 初始化两个插件，并保留现有 opener、dialog、global-shortcut 插件。
- 在 `src-tauri/capabilities/default.json` 增加 `updater:default` 与 `process:default` 权限，只继续授予当前 `main`/`quick` 窗口，不扩大窗口边界。

## 2. 配置签名更新产物

- 在 `src-tauri/tauri.conf.json` 增加：
  - `bundle.createUpdaterArtifacts: true`
  - `plugins.updater.pubkey`
  - HTTPS endpoint：`https://github.com/hahaha-taotao/sealbox/releases/latest/download/latest.json`
  - Windows updater 安装模式使用可见但非浏览器的安装流程，并兼容现有 NSIS `installMode: both`。
- 执行一次 Tauri signer 密钥生成：私钥只保存到本机安全位置和 GitHub Actions Secret，绝不写入仓库；公钥写入 `tauri.conf.json`。
- 采用 Tauri 2 普通 updater 产物：Windows x64 NSIS 安装包、对应 `.sig` 和 `latest.json`。不继续使用当前未签名的浏览器下载链路。

## 3. 重构更新前端流程

- 新增 `src/lib/updater.ts` 作为薄封装，调用官方 `check()`、`Update.download()`、`Update.install()` 和 `relaunch()`，把插件事件归一化为 UI 所需的下载进度。
- 在 `src/App.vue` 将现有 `openUpdateUrl(updateCheck.installer.url)` 流程改成状态机：
  - `idle/checking/up_to_date/available/downloading/ready/installing/error`
  - 保存版本、发布时间、更新说明、下载字节数、总大小、百分比和错误信息。
- “检查更新”改为调用官方 endpoint；没有更新时显示已是最新；有更新时显示版本与 Release notes。
- 将“下载最新程序包”改为“下载更新/立即安装”流程：
  1. 在应用内下载并显示进度；
  2. 下载完成后显示“准备安装”，让用户确认；
  3. 安装前尽力锁定金库、清理前端明文状态，再调用 updater 安装；
  4. 安装完成后调用 `relaunch()`；若系统已接管退出而重启调用失败，明确提示用户手动启动。
- 下载/安装失败时保留已成功获取的版本和更新说明，提供重试；不再把错误时的全部更新元数据清空。
- 没有可用签名更新元数据、检查失败或当前版本仍属于旧版时，保留“打开发布页”作为 fallback，但只打开 Release 页面，不再直接打开未签名安装包 URL。
- 更新 `src/styles.css` 增加进度条、下载详情、安装就绪、错误重试和重启提示样式，适配现有 960x640 最小窗口。

## 4. 移除重复的非签名安装包路径

- 前端不再使用 `InstallerAsset` 和自研 `check_for_updates` 来下载或执行安装包。
- 删除或停用 `src-tauri/src/update.rs` 及 `lib.rs` 中对应 command 注册，避免仓库同时维护两套互相矛盾的更新协议；`opener` 仍保留给 Release 页面、扩展页面等其他外部链接。
- 现有自研更新器单测会随命令移除；新增的信任边界由 updater 的签名校验承担，前端只测试状态转换和进度处理。

## 5. 建立可发布的 GitHub Actions 流程

新增 `.github/workflows/release.yml`，仅在 `v*` tag 触发：

1. checkout、安装 Node/Rust、`npm ci`；
2. 运行版本一致性检查，确保 tag、`package.json`、`Cargo.toml`、`tauri.conf.json`、扩展 manifest 和 lockfile 版本一致；
3. 运行 `cargo test --manifest-path src-tauri/Cargo.toml`、前端生产构建和 `node --test extension/fill-logic.test.js`；
4. 使用 `tauri-apps/tauri-action` 构建 Windows NSIS updater 产物；
5. 通过 `TAURI_SIGNING_PRIVATE_KEY`（以及可选密码）签名；私钥仅从 Actions Secret 注入；
6. 上传 NSIS、`.sig` 和 `latest.json` 到正式 GitHub Release，并只在全部检查通过后发布。

新增一个版本校验脚本（例如 `scripts/check-version.mjs`），避免以后只更新了前端版本而 Rust/安装包仍是旧版本。

## 6. 文档与兼容说明

- 更新 `README.md` 的更新说明、构建/发布说明和 Secret 配置说明。
- 明确说明：现有 v0.1.4 及更早安装包没有 updater 能力，第一次升级到带 updater 的版本仍需手动安装一次；之后才可以完全在应用内更新。
- 保留安装范围可变、per-user/per-machine 和 UAC 的说明；更新不会触碰 `%APPDATA%\\com.sealbox.app\\vault.db`，安装器替换的是程序文件。

## 7. 验证方式

实现后按仓库现有门槛验证：

- `npm run build`
- `cargo test --manifest-path src-tauri/Cargo.toml`
- `node --test extension/fill-logic.test.js`
- 使用临时测试签名密钥执行一次本地 Tauri NSIS 构建，确认生成安装包、`.sig` 和 updater metadata 所需产物；测试密钥不提交。
- 对更新状态覆盖：检查中防重复点击、无更新、有更新、下载进度、下载失败重试、下载完成待安装、安装失败、重启失败和 Release 页面 fallback。
- 最后运行 `git diff --check`，并检查工作树中没有私钥、安装包、`latest.json` 或临时签名文件被误加入版本库。
